# Configuration, identities and credential placement

**Non-secret configuration.** Keep `pilot.json` on the automation project's protected default branch. `repository` is one GitLab namespace/project and `base` is the single target branch. The CI jobs derive the API URL from GitLab's predefined `CI_API_V4_URL`; this starter assumes the automation project and target are on the same GitLab instance. Set the private feed URL exactly as shown in Azure's **Connect to feed** flow, and choose one existing private package for `privateProbe`. Use an HTTPS URL ending in `/npm/registry/`. The starter routes npm traffic through one Azure feed. If the workspace requires several registries or per-scope routing, extend the policy and test those paths before enabling writes. Network egress rules should enforce the company's public-registry policy.

**Secrets.** Prefer the organization's secret manager with job-bound identity. The scripts expect runtime environment variables; protected, masked/hidden GitLab variables scoped to the indicated environments are a pilot alternative. Configure separate values for the same variable name per environment. Confirm environment scoping on your actual subscription and installation. If it is unavailable, inject from separate identities/secret-manager rules or separate protected automation projects before configuring writer secrets. Leave ad hoc pipeline variable overrides disabled.

| Variable | Environment | Purpose |
| --- | --- | --- |
| `PILOT_IMAGE` | All jobs | Approved pullable image digest. The runner must already have registry access. |
| `BOT_USER_ID` | All jobs | Numeric ID of the **target writer** bot, not the reader. Obtain once via authenticated GitLab `GET /api/v4/user` with the writer identity; record only the ID. |
| `GITLAB_TOKEN` | discovery | Reporter or equivalent on the target; read API and repository scopes, including clone. |
| `GITLAB_TOKEN` | ticket-first | Target-project bot, Developer with API access. Permit bot feature branches, deny direct pushes to and merges into protected main. |
| `GITLAB_TOKEN` | review | Separate read-only target identity able to list MR commits, diffs, pipeline jobs and repository files. |
| `AZURE_FEED_TOKEN` | discovery, ticket-first | HTTPS Basic-compatible Azure feed credential for package reads (raw token). Prefer separate credentials per job. Metadata and package tarballs must both be readable. |
| `JIRA_EMAIL`, `JIRA_TOKEN` | ticket-first | Cloud account email and its scoped API token; Data Center uses only `JIRA_TOKEN` as a PAT. Authorize Story browse/create/search and issue links in the pilot project. |
| `JIRA_EMAIL`, `JIRA_TOKEN` | review | Independent Jira reader with Story and link read access. |
| `PILOT_WRITE_ENABLED` | ticket-first | Set to `true` only after the read-only phase passes. Unset to prevent a new writer run. |
| `PILOT_STATE` | ticket-first | CI YAML sets this to the writer-only persistent volume path. |

**Jira Cloud.** Set `kind` to `cloud` and `apiBase` to `https://api.atlassian.com/ex/jira/<cloud-id>/rest/api/3`. The site’s `/_edge/tenant_info` returns the cloud ID. The adapter uses scoped-token basic auth and enhanced JQL search. Classic `read:jira-work` and `write:jira-work` cover the pilot writer; the reader needs read access. Project permissions and required fields still apply. Set your project key and issue type, plus project-specific required fields in `extraFields` (for example a custom field ID). Reserve the label, summary, project and issue type for the coordinator. [Atlassian token setup](https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account/) · [Issue API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/) · [Remote links](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-remote-links/)

**Jira Data Center.** Confirm the edition with the Jira owner; SSO and a company hostname alone do not identify it. Select `data-center`, set the full context path such as `https://jira.company.example/jira/rest/api/2`, and supply an approved integration account PAT. This adapter uses Bearer authentication, REST v2 JQL search, issue creation, and remote links. Test against your specific version, required scheme fields, issue linking settings and PAT policy before enabling the writer. [Data Center personal access tokens](https://developer.atlassian.com/server/jira/platform/personal-access-token/)

**Target application CI.** Keep the non-secret registry route in the target project (see [sample npmrc](../examples/target.npmrc)). The example expects `TARGET_USER_NPMRC` to contain the path to a readable file (e.g. a file-type CI variable or a secret-manager mount). Provide a temporary user-level authenticated npmrc from the target CI secret mechanism for its frozen install, scoped to the exact Azure feed's registry and parent npm paths. Use the feed owner's actual settings for both metadata and tarballs. Target MR jobs may not receive protected variables on unprotected source branches. Have the platform owner provision a read-only feed mechanism suitable for the trusted sandbox MR pipeline and test it from that pipeline. Keep Jira and GitLab writer credentials solely in automation. [Microsoft feed configuration](https://learn.microsoft.com/en-us/azure/devops/artifacts/npm/npmrc?view=azure-devops)

**Merge policy.** In the target project protect the default branch, deny direct bot pushes and bot merges, require the successful MR pipeline and independent human approvals, and configure invalidation on new commits. Check what the installed GitLab tier enforces. Set both squash and merge commit message templates to start with `%{title}`. Confirm squash-before-merge and inspect landed commits. GitLab is the enforcement point; the separate report job is advisory. [GitLab approvals](https://docs.gitlab.com/user/project/merge_requests/approvals/) · [Commit templates](https://docs.gitlab.com/user/project/merge_requests/commit_templates/)
