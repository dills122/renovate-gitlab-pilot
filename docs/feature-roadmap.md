# Renovate experiments for an enterprise Angular, Kotlin, NestJS and Python portfolio

**Decision, 2026-11-04.** Which features should enter the ticket-first pilot next? Start with real workspace coverage and enforceable change controls. Then onboard the cheapest additional service and investigate one JVM service and one Python pipeline independently. Budget one representative repository per ecosystem, one ordinary patch and one negative case per experiment. Stop expansion when a package source, expected change, required CI check or ticket cannot be verified. The recommendations below are proposed experiments, not enabled features.

**Starting evidence.** GitLab EE 18.11.14 and Renovate 44.216.2 have already demonstrated one grouped Angular patch, real Jira Story reservation before the first commit, rerun reuse, and keyed squash and merge commits in a synthetic fixture. The portable coordinator currently accepts exact npm patch pins in one manifest and section per group and expects a manifest plus the pnpm lockfile. It selects one group per pipeline. The report-only review is manual. A Kotlin, Python, catalog, migration or lockfile-only change needs its own artifact parser, update rules and review checks. Enabling a Renovate manager alone does not extend those controls.

## First experiments

| Priority | Feature and reason | Small test and pass condition |
| --- | --- | --- |
| 1 | **Angular and Nx group coverage through the real Azure feed.** Workspaces often declare versions in more places than the fixture. Renovate's npm manager understands pnpm catalogs and reports catalog-specific dependency types. | Inventory one real workspace: root and app manifests, pnpm catalog entries, peer ranges, Angular CLI/build tools, Angular Material/CDK if used, and installed Nx plugins. Compare native dry-run output with a manually enumerated list. Propose separate framework, Nx, and UI component groups only where compatibility demands it. Pass when every intended member is accounted for, an incomplete group is held, and MR CI performs a cold frozen install through the feed plus builds/tests for affected apps. [Renovate npm manager](https://docs.renovatebot.com/modules/manager/npm/) · [Built-in group presets](https://docs.renovatebot.com/presets-group/) |
| 2 | **Central policy and merge enforcement.** Shareable presets distribute defaults across teams. Keep the repository allowlist, write identity, ticket requirement, reviewer, release exceptions and automerge boundary under platform control. | Try overriding policy in a target MR, add an unkeyed commit, run green CI without human approval, then push after a human has approved. Pass only if protected settings enforce your policy on the latest SHA. Inspect every commit introduced by the configured squash merge. Record who may bypass a rule. [Shareable presets](https://docs.renovatebot.com/config-presets/) · [GitLab approvals](https://docs.gitlab.com/user/project/merge_requests/approvals/) · [Renovate GitLab security](https://docs.renovatebot.com/gitlab-bot-security/) |
| 3 | **Release age and MR volume.** Try a three-day minimum for routine patches, two open MRs and one new MR per hour per repo as starting values. Define an org-wide budget separately. | Use a release inside the waiting period, a missing release timestamp from the proxy, and a repo already at its cap. Expect zero new Stories or MRs while held. After eligibility, expect one Story/MR. Record actual timestamps and decisions. Add a coordinator check before Jira reservation and recheck before writing. Renovate's per-repo limits alone cannot bound an enterprise fleet. [Minimum release age](https://docs.renovatebot.com/key-concepts/minimum-release-age/) · [Release timestamp behavior](https://docs.renovatebot.com/configuration-options/#minimumreleaseagebehaviour) · [MR rate](https://docs.renovatebot.com/configuration-options/#prhourlylimit) |
| 4 | **Nx migrations and major-update visibility.** Use the Dependency Dashboard to surface larger changes for owner triage. Dashboard approval controls whether Renovate proposes an update; GitLab governs approval to merge. Nx migrations may update code and config in addition to versions. | Take one representative minor/major upgrade. Have the owner generate and run the Nx migration plan in a sandbox, inspect source/config diffs, run affected tests and one full build, and compare against a simple dependency bump. Route migration changes to explicit human review. Keep the standard patch writer's narrow file allowlist. [Nx update workflow](https://nx.dev/docs/features/automate-updating-dependencies) · [Dependency Dashboard](https://docs.renovatebot.com/key-concepts/dashboard/) |

Dashboard behavior needs a deliberate design in this pilot. Discovery currently runs in lookup mode and the writer disables the dashboard. First publish a read-only inventory of held/major candidates in automation artifacts. If a team wants native dashboard controls, test a separate trusted run and prove a dashboard checkbox cannot bypass ticket reservation or protected approvals.

## How to bring in the other stacks

| Stack | What to investigate | Acceptance test |
| --- | --- | --- |
| **NestJS APIs**, if confirmed | Reuse the npm manager. Check whether manifests use exact pins, caret ranges, or workspace/catalog references. Group tightly coupled framework packages such as core, common and the installed HTTP platform adapter only when their peer constraints warrant it. Inspect Swagger, ORM and other plugins independently; sharing the Nest scope does not imply a common release version. | One framework patch, reproducible install and old/new API contract comparison. Exercise application startup, one authenticated route, serialization and error responses. A typecheck alone cannot show that a request still works. Confirm the production adapter and package manager with the service owner. [Renovate npm support](https://docs.renovatebot.com/modules/manager/npm/) |
| **Kotlin/JVM microservices** | Inventory the build tool first. For Gradle, test Kotlin DSL, `gradle/libs.versions.toml`, plugin declarations, dependency verification and the wrapper separately. For Maven, inspect the POM, parent/BOM and managed versions. For a BOM-managed library, update the controlling BOM and verify the resolved graph. Keep Kotlin compiler/plugin, framework BOM, Gradle wrapper and JDK upgrades distinct from ordinary library patches. | Compare Renovate's extracted versions with the service's resolved dependency graph. Run one ordinary patch, build and integration tests against the company Maven repository, and inspect lock/verification changes. Gradle extraction can work without executing the wrapper; lock or checksum regeneration may need wrapper execution. If needed, isolate it on a trusted worker, with no Jira credentials in the build environment. Roll the same library through one canary service before expanding. [Gradle manager](https://docs.renovatebot.com/modules/manager/gradle/) · [Maven manager](https://docs.renovatebot.com/modules/manager/maven/) |
| **Python data science** | Ask which file drives deployment: requirements inputs/compiled output, Poetry, uv/pyproject, or another environment system. Match the actual manager rather than guessing from the presence of a requirements file. Renovate supports PEP 440 versions, so do not reuse the npm three-part patch parser. | Rebuild a clean environment using the production Python version and package index. Run one fixed dataset and seed through the pipeline. Have the owner specify acceptable output/metric tolerance up front. Check wheel availability on the production architecture, native library imports, and CPU/GPU variant where relevant. Hold if installation passes but results drift. [Python support](https://docs.renovatebot.com/python/) · [uv/PEP 621 manager](https://docs.renovatebot.com/modules/manager/pep621/) · [pip-compile manager](https://docs.renovatebot.com/modules/manager/pip-compile/) |

## Features to add after the first routine patches

- **Scheduled lockfile maintenance.** Test a change to transitive dependencies while the manifest stays unchanged. Give this operation its own Jira identity (repo, branch, lockfile and maintenance cycle), MR class and reviewer policy. The current group+version identity and manifest-change requirement do not cover it. Start with one pnpm workspace and review transitive churn alongside frozen CI. [Lockfile maintenance](https://docs.renovatebot.com/configuration-options/#lockfilemaintenance)
- **Security remediation with an expedited path.** Trial one known vulnerable fixture and an unaffected control. Renovate's OSV alerts cover direct dependencies for supported datasources. Keep your existing GitLab/security scanner for transitive and broader coverage. Explicitly decide whether security fixes can bypass release age or normal volume limits, who authorizes that exception, and whether the worker can access the advisory source. The ticket, CI and human approval must still be verified. A security fix outside the current patch/minor line needs a separate review path; do not widen the routine patch writer to make it pass. [OSV alerts and limitations](https://docs.renovatebot.com/configuration-options/#osvvulnerabilityalerts)
- **Shared CI image and build-tool updates.** Once application updates are stable, test one approved CI base-image digest or a Gradle wrapper upgrade as its own ticket category. Run the downstream build image or wrapper on a disposable worker. This has much broader impact than a single library patch. [Dockerfile manager](https://docs.renovatebot.com/modules/manager/dockerfile/) · [Gradle wrapper manager](https://docs.renovatebot.com/modules/manager/gradle-wrapper/)
- **Reviewer in shadow mode before any auto-approval.** Have the report-only reviewer classify a run of real patches, then compare its decisions with independent human reviewers. Count false eligible decisions, holds, missed dependencies, duplicate/orphan Stories, time to review, and stale-SHA decisions. Suggested promotion gate: zero false eligible decisions, duplicate tickets and unkeyed landed commits in the pilot sample; investigate every disagreement. Define sample size and any future automated approval with the control owner. Keep automerge off during this investigation.

## Evidence to retain

For each merged change, retain the ticket and creation time, update reason/category, MR and commit keys, base/head SHA, CI job results on the actual head, human approver and time, final landed SHAs, and policy version or automation commit. Exercise denied paths as well as successful ones: expired Jira credential, missing private package, timed-out ticket creation, stale pipeline and approval invalidation. Verify that the records remain accessible for the organization's retention period. A seven-day CI artifact alone is insufficient if the internal retention period is longer.

Ticket-at-first-commit is the requirement reported by this organization. The compliance owner determines how these tests and evidence map to its change-management, access and monitoring controls. A Renovate setting or successful lab run cannot establish SOC 2 compliance. [AICPA Trust Services Criteria](https://www.aicpa-cima.com/resources/download/2017-trust-services-criteria-with-revised-points-of-focus-2022)

This was syntax validation only. No features were enabled and no work repo, ticket or MR was accessed.
