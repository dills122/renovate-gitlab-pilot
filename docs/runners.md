# Worker image and runners

The runner is the GitLab agent. It pulls the worker image and launches a fresh Docker job container. Start with two protected project runners, one tagged `protected-renovate-discovery` (discovery and read-only review), one tagged `protected-renovate-writer` (writer only). One protected runner with disposable job containers is possible if platform approves the shared host trust boundary. The sample registration scripts assume two Linux Docker runners and one persistent writer host.

1. **Build.** On an approved build host with access to the pinned base image and pnpm tarball, run the commands below. Example values are illustrative. Replace the image registry path and architecture with platform's confirmed values. If work builds must fetch via an internal mirror, mirror the base image/tarball first, verify the checksums, and change the Dockerfile's source URLs.
   ```sh
   IMAGE_TAG='REGION-docker.pkg.dev/PROJECT/REPOSITORY/renovate-pilot:44.216.2-pnpm10.23.0'
   docker buildx build --platform linux/amd64 --tag "$IMAGE_TAG" --push .
   docker buildx imagetools inspect "$IMAGE_TAG"
   ```
   Record the pushed manifest digest. Set the automation project's protected `PILOT_IMAGE` variable to the full image reference ending in `@sha256:…`. Confirm the image contains the versions the workspace expects: `renovate --version`, `node --version`, `python3 --version`, `pnpm --version`.
2. **Runner host.** Platform supplies an isolated non-production network route, trusted CA chain and DNS for GitLab, Jira, the Azure feed and the image registry. Use its approved pull mechanism (runner identity/credential helper or scoped Docker auth). Image pull happens before the job starts. Bake enterprise CAs into an approved image or mount them and configure OS/Python, Node and Git consistently. Set actual proxy/NO_PROXY settings on both the runner and job if needed. Test cold pulls and registry access from the workers themselves.
3. **Create runners.** In the automation project's runner settings create each project runner with its tag, **Protected** enabled, **Run untagged jobs** off, and project lock enabled. Keep the authentication tokens in the runner service's secure config. Use a supported GitLab Runner version matching your GitLab platform policy. [GitLab runner registration](https://docs.gitlab.com/runner/register/)
4. **Register.** On the Linux runner manager, set `CI_SERVER_URL`, `PILOT_IMAGE`, and supply the correct `RUNNER_TOKEN` through a secret or hidden prompt. Execute the registration script as the account responsible for the runner config. For the writer first set `STATE_DIR` (for example `/srv/renovate-pilot-state`), run `sudo ./scripts/setup-state.sh "$STATE_DIR"`, then run `./scripts/register-runner.sh writer`. For discovery run `./scripts/register-runner.sh discovery`. Unset `RUNNER_TOKEN`. The state setup assumes the image user UID 12021; adjust ownership for your runtime. Start/reload the runner service and confirm both are online. Do not mount the Docker socket or host credentials into jobs. Use unprivileged containers; restrict allowed images to approved repositories.
5. **Verify isolation.** Inspect the runner assignment on the first job. Only writer jobs should see the state marker and Jira writer/GitLab writer credentials. The read-only review job may see its own separately scoped Jira reader. Avoid debug traces, reused privileged shell runners and shared untrusted projects.
6. **State service level.** The provided writer uses SQLite on a dedicated local persistent filesystem and a GitLab resource group to serialize jobs. Back up the state directory while writes are paused, and test restoring it on the designated replacement worker. Use one writer host. For ephemeral Cloud Run or multiple independent workers, implement reservation storage in an approved transactional database before rollout; local disk per worker cannot provide the same guarantees.

The source image and scripts can also be included in an existing enterprise runner build process. The provided jobs expect Docker executor image selection to work. Copying them to an SSH/shell executor requires preinstalling the toolchain and isolating secrets at the host level.
